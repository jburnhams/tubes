## 2026-11-09: signed in to a Premium account

- Asked for: use the owner's Google account (YouTube Premium) so the ad wait goes.
- Measured on the same eight videos with yt-dlp reading a signed-in Chrome profile on the server (`--cookies-from-browser chrome+gnomekeyring`; without `+gnomekeyring` nothing decrypts under that desktop): yt-dlp saw Premium, every playable video offered ad-free 1080p AV1/VP9, no "Sleeping ... as required by the site" and no 403s. First segment 5-7 s after Play on every video (was 8-13 s where the ad wait applied; the few videos `visionos` plays signed out start 2-3 s slower signed in). It works from a systemd user service, as long as the desktop keyring is unlocked (autologin). Reading the cookies costs about 0.1 s.
- Clients signed in: `tv_downgraded` gave 1080p with the fastest probes (3.7-5.5 s); default, `web_creator` and `mweb` also work; `web_safari` and `tv` gave 360p only (SABR); `visionos` takes no cookies and is skipped. Premium-only formats (616) need a PO token and did not appear.
- New setting `cookies_from_browser` (empty by default: signed out). When set, every yt-dlp call gets `--cookies-from-browser`, including the two downloads (the saved probe holds no cookies), and `visionos` is swapped for `tv_downgraded`. Reading the live profile rather than an exported cookies.txt keeps the session fresh, since the browser refreshes it.

## 2026-11-09: why videos start slowly on the server

- Asked for: the deployed server took about 13 s from Play to the first segment, against about 2 s in the spike; check other videos and clients.
- Measured on eight library videos with the deployed yt-dlp (2026.10.26): YouTube answered the `visionos` client with UNPLAYABLE for six of the seven that play here, and yt-dlp then falls back to `web_embedded`, which carries an ad and makes the download wait 4-10 s "as required by the site". The spike's videos happened to be ones `visionos` plays. No other client (tv, tv_simply, tv_downgraded, web, web_safari, mweb, ios, android, android_vr, default) gave 1080p without that wait: unplayable, images only, or 360p without a PO token. Skipping the wait gets a 403, and it counts from the end of extraction, so it is paid once whatever the order.
- Time to first segment = probe (about 3.5 s) + each download extracting again (about 3.5 s) + the wait (0-10 s). The downloads now reuse the probe (`--load-info-json` with the probe saved as `probe.json` in the video's folder, deleted at the end), which removes the second extraction: measured 3-4.5 s without the wait (was 5-8 s) and 8-13 s with it (was 12-17 s). It also stops a chosen format vanishing between two extractions ("Requested format is not available").
- About one probe in eight came back with only SABR streams (no https formats); a probe whose streams cannot be chosen is now tried once more. Twice a download got a 403 after its wait and not on retry; not handled yet.
- `visionos` stays: fastest where it works, free where it does not (yt-dlp adds `web_embedded` itself). Going lower for the slow videos would need a PO token provider (none installed), which might open `mweb` or `web` at 1080p; a separate experiment. Fetching likely videos ahead of time (milestone 4) avoids the wait altogether.

## 2026-11-09: Tubes rebuilt as a home video server (milestone 1)

- Asked for: replace the old in-browser player (a YouTube-like UI and a browser-side stream extractor through a VPS proxy, abandoned in January 2026: datacenter IPs were bot-checked, and stream URLs and tokens broke constantly) with a server that fetches with yt-dlp on the home connection. Built from python-app-template.
- Spike, on the home server, three public videos, no cookies: downloads ran at 100–250 Mbit/s (a 36-minute video in 31 s); the first HLS segment was ready in 7.8 s with yt-dlp's default clients and 2.1 s with `--extractor-args youtube:player_client=visionos` (the defaults wait 4 s). H.264 and VP9 played cleanly; AV1 was offered on all three at about half H.264's size, so the order is AV1 > VP9 > H.264 and 1 TB holds 2,000+ hours at 1080p. ffmpeg fetching the stream URLs itself got 403, so yt-dlp downloads and pipes into ffmpeg. Format choice must check width as well as height (a wide film's 1080-high format is 2560 wide) and prefer the original audio track over dubbed ones.
- Changed plan: Tubes is generic, with no curation or viewer screens. The library is managed in the existing library app (a Cloudflare Worker that writes D1), as the old app did; Tubes reads D1 directly (SELECT only, credentials from the environment) and keeps a local copy, because a D1 query takes 0.4–0.5 s.
- Changed plan: Tubes' tables live in its own schema of the shared Postgres through omarchy_db (library, `dbtool` migrations, pytest plugin), not a JSON or SQLite file. Tests run on SQLite; `--pg` runs them on Postgres, and both pass (the first migration had to be generated against Postgres: generated against SQLite, a boolean default came out as `0`, which Postgres refuses).
- Web: seven screens on strata-react 0.1.17 (from npm), with a palette generated from the subject (a screen's blue-green and a lamp's amber) in place of the template's. 73 web tests at 100% coverage; 136 screenshot baselines (44 stories and 12 route states, light and dark). The visual build gets a root `<base href>` (`vite build --mode visual`) because the plain static server the visual runner uses does not add the one the Python server adds, and deep routes such as `/channels/x` otherwise load their assets from the wrong folder.
- Open: `InfiniteList` is always its own scroll box (480 px by default; 720 here), so a channel's videos scroll inside the page rather than with it.
- Changed plan: the watching screens first took Strata's look, which was a misreading of "keep our look and feel": it meant the old Tubes look. The watching side (`web/src/watch/`) is back to a video site's layout (top bar with search, a rail with every channel, chips, rounded thumbnails with the running time, "views · age", Up next beside the player) with Tubes' own red mark and `tube-*` tokens; Strata's look stays for the admin area under `/admin`. The watching side pages by scrolling (an IntersectionObserver sentinel plus a Show more button), which also removes the `InfiniteList` scroll box above. Browse's shuffle became Home's newest-first grid (the shuffle feeds Up next). 85 web tests at 100% coverage; 140 baselines.

## 2026-11-09: web app rebuilt on strata-react

- Asked for: make the template use strata-react fully, as an example and starter for new apps, with Storybook and visual testing.
- The web app is now four screens built only from strata-react (`web/src/screens/`), each opening with its one question and the patterns it shows: Greetings (`useLoad` → `DataView` → `DataTable` with sort in the URL, `RowAction` + `useUndoable` + `UndoBar`, `useSelection` + `BulkBar`, `Field` + `AsyncButton`, `MetricStrip`), Log (`useInfiniteLoad` over a cursor API → `InfiniteList`), System (polled read with `StaleNotice`, `Meter` with thresholds, `CompositionBar`, `Status`, `LinkCard`) and Settings (`Tabs` in the URL, a form started from the server's values, `ColorSchemeChoice`). The hand-written `ui.tsx`, hash router and `useLoad` are gone.
- Routing moved from `#/` hashes to real paths with React Router. To keep one build working behind a reverse proxy at a prefix, the server now answers every non-API path with the app and adds a relative `<base href>` that leads back to its root (`with_base` in `server/app.py`); `api.ts` `BASE` reads it and React Router takes it as `basename`. Checked by hand through a proxy at `/pre/`: deep links, a nested unknown path, sending and removing all worked with no failed request.
- API: `GET /api/system` (`system.py`), `GET /api/messages/page?after=&limit=` (a cursor, not an offset) and `DELETE /api/messages/{id}`. Ids were `len(items) + 1`, which reuses an id once a greeting is removed; they now come from `messages.seq` and are never reused (the web app hides a removed row by id until the removal commits, so a reused id would hide a new greeting).
- Theme: generated by ux-research `palette.mjs` from the subject (postmark ink and stamp red; 42 checks pass); status roles reuse strata-react's fixture values after measuring them on this palette's grounds (every ink at least 6.0:1). Faces are bundled (`@fontsource-variable`), which the visual suite requires.
- Tests: the jsdom suite renders the app's own route tree with `renderRoutes` from `strata-react/testing`, against MSW handlers that now live in `web/src/mocks/` and also serve Storybook and the visual suite. 40 web tests, 100% coverage (floors raised to 100); Python unit coverage 100%.
- Visual: `strata-visual` screenshots every story and the production build's routes (wide and phone) light and dark: 76 baselines, written here in the pinned Chromium (Playwright 1.63.0) and re-run clean. A long, auto-paging log is not screenshotted: which rows are in view depends on when pages land (CI and this machine disagreed on the first run); its paging is covered in jsdom. New CI job `visual` in `unit.yml`.
- Gaps in strata-react, raised as issues rather than worked around: `HttpError` drops the response body, so the server's 400 reason (`detail`) cannot be shown and `api.ts` repeats the server's limits client-side (jburnhams/strata-react#42); `CompositionBar` prints 0% for a part that is small but not zero (jburnhams/strata-react#43).
- One filled button at a time: a review saw the bulk "Remove 2" and "Send greeting" both filled once rows were chosen. The ux-research docs said "one filled per view" and "BulkBar: one filled" without saying which wins; the decision (recorded in ux-research `ui-library/patterns.md` §2 and strata-react's `CLAUDE.md`) is that while rows are chosen the bulk action is the filled one and the screen's primary steps down to outline. `GreetingForm` takes `primary`; the bulk-bar test checks exactly one filled button before, during and after a selection; the four `greetings--selected` baselines changed for it.
- Left out on purpose, as this sample has no use for them: keyboard queues (`useActiveItem`, `useHotkeys`), `SelectableGrid`/`Thumbnail`, `LineChart`, `Disclosure`/row expansion, `Done`.
