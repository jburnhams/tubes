# Repository Guidelines

Tubes: a home video server that keeps a video library of YouTube channels and videos (added in its admin area, details from the YouTube Data API), fetches a video with yt-dlp when it is first played, streams it as HLS while it downloads and keeps copies in a size-capped cache. Python backend (FastAPI + CLI) and React frontend built on [strata-react](https://github.com/jburnhams/strata-react) (TypeScript + Vite + Tailwind CSS v4), from python-app-template, with hermetic unit and integration test suites, Storybook, screenshot tests, coverage ratchets and multi-OS GitHub Actions CI.

- Keep code, docs, fixtures and tests generic: no real channel, video or viewer is named anywhere in the repo; which channels are followed is data. The library is managed here (`catalogue.py` writes, `library.py` reads, `youtube.py` calls the Data API, `quota.py` counts each call against the daily quota; ported from the storage service in 2026-11); `history.py` imports a watch history (Google Takeout) and suggests channels from it; `related.py` adds the channels the followed and most watched ones point at (their watch pages' next column, read signed out, and the channels they feature), asked again weekly by `tubes related`; `paste.py` reads a pasted list (YouTube and iPlayer links, @handles or names) into the suggestions; `iplayer.py` adds BBC iPlayer programmes (kept as channels) and episodes (as videos, `platform` 'iplayer'), fetched by ffmpeg alone; `iplayer_suggest.py` suggests iPlayer programmes like those followed or played, from a daily copy of iPlayer's catalogue. `viewing.py` keeps what is watched here (each play's source, seconds seen and outcome: short, partial, full at 90%; each channel page visit), which Continue watching, Up next and later recommendations read. `plex.py` adds a Plex Media Server's films and shows (`platform` 'plex'; a show is a channel, a film goes under the Plex Films channel, a followed filter of a library is a channel of its own), its pictures served through Tubes so the token (`PLEX_URL`, `PLEX_TOKEN` from the environment) never reaches a browser, and its files read by ffmpeg (copied, or converted here for a browser that cannot play them: fetcher.plex_copy; Plex itself never transcodes). A break (settings `break_*`, `GET /api/break`, `web/src/watch/break.tsx`) pauses the video after so many minutes of playing and shows a configured page over the picture until it posts `{type: 'tubes:done'}` to its parent or a time limit passes; Tubes knows nothing else of that page. `metadata.py` holds the metadata shape every source fills as far as it can, modelled on Plex's (kind, tagline, year, network, season, ratings for age, kids, picture size; images, tags, credits, ratings, external ids, chapters and tracks in tables of their own). `groups.py` keeps groups of videos, which may overlap, loaded whole from a file made outside (`tubes groups load`): the Groups page. `prefetch.py` fetches the first seconds of the videos Home, Up next and a channel's page offer, kept as partial copies, so a play starts at once (cache.py's notes). What the watching side lists is one rule, `library.shown()` (not gone, not refused as blocked in this country, not expired, not a stream live now, and Admin's length, stream, country, language and captions filters from Settings > Shown videos, kept in `meta`); every list and count goes through it. Credentials only come from the environment (`YOUTUBE_API_KEY`, `YOUTUBE_API_REFERER`).
- Shared server code comes from [strata-python](https://github.com/jburnhams/strata-python) (PyPI, `strata-python[db]>=0.2.10,<0.3` in `requirements.txt`; read its README, "Move an app onto it"): settings (`settings.py` only declares them on its `Settings`), the server's health, settings, error handlers (`server/app.py`'s `ERRORS`, a status or a function of the exception), web app and runner (`web.base_app`, `add_error_handlers`, `add_web`, `serve`), the `doctor`/`set`/`serve`/`openapi` commands, the HTTP client every outside service is asked through (`http.Http`: one per module, with its pace and retries), the prefetcher's loop (`tasks.Ticker`), `oslib`, atomic files, the database, the pytest plugin and the `strata-check` gate (`scripts/check`). Do not copy those back into Tubes; if strata-python lacks something, raise an issue there (a stand-in here stays small and says so).
- Tubes' tables live in its own database through `strata_python.db` (`src/tubes/models.py`, migrations in `migrations/`, `[tool.strata-db]` in `pyproject.toml`): `strata-db revision -m "..."` after changing a model (generate against Postgres, so server defaults come out portable); `tests/unit/test_db.py` runs strata-python's standard migration and drift tests on SQLite and with `--pg` on Postgres. A real Postgres needs `STRATA_DB_LIVE=1` and `STRATA_DB_DATABASE` (or `TUBES_DATABASE_URL`) in the environment, and is always refused under pytest. SQL in `library.py`, `catalogue.py` and `cache.py` must run on both (SQLite in tests, Postgres in production); run the Python suites with `--pg` to check against a local Postgres.
- API types: `web/src/api.generated.ts` is generated from `web/openapi.json` (`./tubes openapi -o web/openapi.json`, then `npm run api-types` in `web/`) and never edited; after changing a route or a request model run both (the Python unit suite and CI's `api-types:check` fail on a stale one). Request bodies in `web/src/api.ts` are checked against it with `satisfies In<'...In'>`. Answers are typed too: each route declares what it returns with `responses=answer(Model)` (models in `src/tubes/server/answers.py`; they document and do not filter), the tests validate every 200 answer against its model (`answers.CHECK`, on in `tests/conftest.py`), and `web/src/api.ts` aliases them (`export type Channel = Schema<'Channel'>`). A new route declares its answer; a new field the web reads goes into its model.
- Python application code lives in `src/tubes/`; the React web app lives in `web/src/` and builds into `src/tubes/server/static/`, which `./tubes serve` serves at every non-API path.
- The web app has two looks, on purpose. The watching side (`web/src/watch/`: Home, Search, Channels, a channel, Groups, a group, Watch, not found) keeps the old Tubes look, a video site's layout (top bar with search, a rail of pages, rounded thumbnails, "views · age") drawn with Tubes' own mark and the `tube-*` tokens in `web/src/styles/tube.css` (Roboto, bundled); never use another site's logo or name. It is built from Strata's components too, given that look by scoping Strata's roles to the viewer shell (`.tube` in `tube.css`: page, ink, chips, round controls, rounded pictures, Roboto), so a Strata component there draws in the old look with no class of its own: every read is `DataView` with the watching side's skeletons, empty states and `trouble` (`watch/Shown.tsx`), the pill is Strata's `Button`, avatars and video pictures are `Thumbnail`, Show more is `LoadMore` with this side's rows, and the Watch page plays through Strata's `MediaPlayer` (`attach` from `strata-react/hls`, `growing` while a copy is fetched, the skippable parts as its `spans`, Picked up at in its `overlay`, the title and channel in its `heading`). Where Strata cannot reach yet (a colour per span kind, a start time, the seconds played: strata-react #270-#272) the piece stays in Tubes and an issue on strata-react asks for it. The web dependencies follow strata-react's stack and versions (TypeScript 7 for `typecheck`, the TS 6 API as `typescript` for Storybook's docgen). The admin area (`web/src/screens/`, under `/admin`: Library, Suggestions, Plex, Viewing, History, Cache, YouTube quota, System, Settings) follows strata-react's rules (its `CLAUDE.md`, "Building an app on Strata"): only Strata components and theme roles (no raw palette colours, arbitrary values or `dark:` overrides), every remote read `useLoad`/`useInfiniteLoad` → `DataView`/`InfiniteList` with skeleton and empty state, one filled button per view at a time (the `BulkBar` action takes it while rows are chosen), reversible removals through `useUndoable`, URL state for sort/tab, numbers and dates through `format`. Each screen in both folders opens with its one question. Something Strata lacks is raised as an issue on strata-react, not hand-built here.
- Python tests live under `tests/`, grouped by type:
  - `tests/unit/`: fast, isolated tests of pure logic and mocked boundaries (synthetic data, fakes). No external processes or network.
  - `tests/integration/`: end-to-end tests that run the CLI (in-process and as a subprocess) and the FastAPI HTTP API over real on-disk state.
  - `tests/utils/`: Tubes' own stand-ins (fake YouTube, iPlayer, Plex and yt-dlp) and helpers. strata-python's pytest plugin makes every suite hermetic (isolated home and data dir, no network; configured in `[tool.pytest.ini_options]`) and gives `fake_urlopen`, `fake_popen`, `fake_run`, `http_server` and the `db_*` fixtures; `tests/conftest.py` holds Tubes' own.
  - Read `tests/README.md` before writing any Python test: fixtures, conventions, file-ownership rules and the per-module coverage ledger.
- Web tests live in `web/tests/{unit,integration,utils}` (vitest; unit runs in node, integration in jsdom through `renderRoutes` from `strata-react/testing`). Backend calls are answered by msw from `web/src/mocks/handlers.ts` (every endpoint the app calls needs a handler there; the same handlers serve Storybook and the visual suite); read `web/tests/README.md` before writing any. Stories live in `web/stories/`; visual baselines in `web/tests/visual/baselines/`.
- Commands (Python, from the repo root, with `.venv` active or via `./tubes` / `tubes.cmd`; `pip install -r requirements-test.txt` is enough for the test suites):
  - `pytest tests/unit --cov` runs the unit suite with coverage (random order via pytest-randomly; `-n auto` runs in parallel; `diff-cover` checks the lines a change touches).
  - `pytest tests/integration -n auto` runs the integration suite.
  - `scripts/check` is strata-python's gate (`--fast` skips the tests, `--fix` applies ruff's safe fixes): `ruff check`, `ruff format --check`, `pyright` (strict over `src/`) and `ty`, then the unit tests with coverage. Run it before every commit; CI runs `--fast` once and the tests on every OS.
  - `./tubes doctor` checks the environment; `./tubes add <link>` follows a channel, `./tubes sync` fetches new videos for every followed channel; `./tubes serve` runs the web server on port 8367. `pytest --pg` runs a suite against Postgres (strata_python.db's pytest plugin; `STRATA_DB_TEST_ADMIN_URL` for a server of your own) instead of SQLite.
- Commands (web, from `web/`): `npm install`, `npm run dev` (proxies `/api` to `./tubes serve` on 8367), `npm run build` (writes into `src/tubes/server/static/`), `npm run typecheck`, `npm run test:unit` (node), `npm run test:integration` (jsdom + msw), `npm run test:coverage:gate` (unit + integration together, what CI gates on: floors in `web/coverage-floor.json`), `npm run test:coverage` (unit only, informational), `npm run test:coverage:all` (unit + integration, no gate), `npm run storybook`, `npm run build-storybook`, `npm run test:visual` (builds the app and Storybook, then `strata-visual` compares every story and route state, light and dark, with the baselines), `npm run test:visual:update` (look at the diffs in `tests/visual/output/` first). Node 26 (`.nvmrc`).
- Python coverage is calculated from the unit suite only (`fail_under` in `pyproject.toml`). Web coverage is gated on unit + integration together (`web/coverage-floor.json`, read by `web/vitest.gate.config.ts`). Both floors only ratchet up.
- Style: dense, comment-the-why, `ruff format` at line length 120 (not by hand; the reformat is in `.git-blame-ignore-revs`), everything in `src/` fully typed and clean under pyright strict and ty (JSON from other services is read through `shape.py`'s `obj`/`arr`/`objs`), pytest style tests (`def test_...` with `assert`; use `monkeypatch`/`tmp_path` instead of patching globals by hand).
- Cross-platform (Linux, macOS, Windows): OS differences (file locks, process liveness and termination, priority, how to start the CLI) live in `strata_python.oslib`; do not import `fcntl` or call `os.kill(pid, 0)` elsewhere (on Windows that terminates the process).
- Reverse-proxy support: the server gives every page a relative `<base href>` back to its root (`with_base` in `server/app.py`), the web build uses relative asset paths (`base: './'` in `vite.config.ts`), and `BASE` comes from the page's base URL (`web/src/api.ts`); it is React Router's `basename`. Any URL the app builds for `fetch`, `<img>` or an external link must go through `withBase`; in-app links are router paths.
- CI is `.github/workflows/unit.yml` (lint, unit tests with coverage on Linux Python 3.11-3.13, macOS and Windows; web typecheck, coverage gate, build, Storybook build; visual regression) and `integration.yml` (integration tests on Linux, macOS and Windows, web component tests, weekly). `scripts/setup_env.ps1` / `setup_env.sh` build the environment from scratch.
- Docs live in `docs/`: `overview.md` (design brief), `implementation-plan.md` (milestones and next steps), `progress.md` (log of findings and decisions), `deploy.md` (running it on a server), `prompts/` (unattended agent prompts for backend unit, integration and web tests).
