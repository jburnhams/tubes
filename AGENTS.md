# Repository Guidelines

Tubes: a home video server that keeps a video library of YouTube channels and videos (added in its admin area, details from the YouTube Data API), fetches a video with yt-dlp when it is first played, streams it as HLS while it downloads and keeps copies in a size-capped cache. Python backend (FastAPI + CLI) and React frontend built on [strata-react](https://github.com/jburnhams/strata-react) (TypeScript + Vite + Tailwind CSS v4), from python-app-template, with hermetic unit and integration test suites, Storybook, screenshot tests, coverage ratchets and multi-OS GitHub Actions CI.

- Keep code, docs, fixtures and tests generic: no real channel, video or viewer is named anywhere in the repo; which channels are followed is data. The library is managed here (`catalogue.py` writes, `library.py` reads, `youtube.py` calls the Data API; ported from the storage service in 2026-11); `history.py` imports a watch history (Google Takeout) and suggests channels from it; `related.py` adds the channels the followed and most watched ones point at (their watch pages' next column, read signed out, and the channels they feature), asked again weekly by `tubes related`; `iplayer.py` adds BBC iPlayer programmes (kept as channels) and episodes (as videos, `platform` 'iplayer'), fetched by ffmpeg alone. Credentials only come from the environment (`YOUTUBE_API_KEY`, `YOUTUBE_API_REFERER`).
- Tubes' tables live in its own database through [omarchy_db](https://github.com/jburnhams/database) (`src/tubes/models.py`, migrations in `migrations/`, `[tool.omarchy-db]` in `pyproject.toml`): `dbtool revision -m "..."` after changing a model (generate against Postgres, so server defaults come out portable), `dbtool check` on SQLite and Postgres. SQL in `library.py`, `catalogue.py` and `cache.py` must run on both (SQLite in tests, Postgres in production); run the Python suites with `--pg` to check against a local Postgres.

- Python application code lives in `src/tubes/`; the React web app lives in `web/src/` and builds into `src/tubes/server/static/`, which `./tubes serve` serves at every non-API path.
- The web app has two looks, on purpose. The watching side (`web/src/watch/`: Home, Search, Channels, a channel, Watch, not found) keeps the old Tubes look, a video site's layout (top bar with search, a rail of pages and channels, rounded thumbnails, "views · age") drawn with Tubes' own mark and the `tube-*` tokens in `web/src/styles/tube.css` (Roboto, bundled); never use another site's logo or name. It still reads through Strata's `useLoad`/`useInfiniteLoad`, shown by `watch/Shown.tsx` with its own skeletons, empty states and Try again. The admin area (`web/src/screens/`, under `/admin`: Library, Suggestions, Cache, System, Settings) follows strata-react's rules (its `CLAUDE.md`, "Building an app on Strata"): only Strata components and theme roles (no raw palette colours, arbitrary values or `dark:` overrides), every remote read `useLoad`/`useInfiniteLoad` → `DataView`/`InfiniteList` with skeleton and empty state, one filled button per view at a time (the `BulkBar` action takes it while rows are chosen), reversible removals through `useUndoable`, URL state for sort/tab, numbers and dates through `format`. Each screen in both folders opens with its one question. Something Strata lacks is raised as an issue on strata-react, not hand-built here.
- Python tests live under `tests/`, grouped by type:
  - `tests/unit/`: fast, isolated tests of pure logic and mocked boundaries (synthetic data, fakes). No external processes or network.
  - `tests/integration/`: end-to-end tests that run the CLI (in-process and as a subprocess) and the FastAPI HTTP API over real on-disk state.
  - `tests/utils/`: shared helpers (`fakes.py` for HTTP/subprocess doubles). `tests/conftest.py` holds shared fixtures and makes every suite hermetic (isolated home and data dir, no network).
  - Read `tests/README.md` before writing any Python test: fixtures, conventions, file-ownership rules and the per-module coverage ledger.
- Web tests live in `web/tests/{unit,integration,utils}` (vitest; unit runs in node, integration in jsdom through `renderRoutes` from `strata-react/testing`). Backend calls are answered by msw from `web/src/mocks/handlers.ts` (every endpoint the app calls needs a handler there; the same handlers serve Storybook and the visual suite); read `web/tests/README.md` before writing any. Stories live in `web/stories/`; visual baselines in `web/tests/visual/baselines/`.
- Commands (Python, from the repo root, with `.venv` active or via `./tubes` / `tubes.cmd`; `pip install -r requirements-test.txt` is enough for the test suites):
  - `pytest tests/unit --cov` runs the unit suite with coverage (random order via pytest-randomly; `-n auto` runs in parallel; `diff-cover` checks the lines a change touches).
  - `pytest tests/integration -n auto` runs the integration suite.
  - `ruff check src tests` lints for syntax errors and undefined names.
  - `./tubes doctor` checks the environment; `./tubes add <link>` follows a channel, `./tubes sync` fetches new videos for every followed channel; `./tubes serve` runs the web server on port 8367. `pytest --pg` runs a suite against Postgres (omarchy_db's pytest plugin) instead of SQLite.
- Commands (web, from `web/`): `npm install`, `npm run dev` (proxies `/api` to `./tubes serve` on 8367), `npm run build` (writes into `src/tubes/server/static/`), `npm run typecheck`, `npm run test:unit` (node), `npm run test:integration` (jsdom + msw), `npm run test:coverage:gate` (unit + integration together, what CI gates on: floors in `web/coverage-floor.json`), `npm run test:coverage` (unit only, informational), `npm run test:coverage:all` (unit + integration, no gate), `npm run storybook`, `npm run build-storybook`, `npm run test:visual` (builds the app and Storybook, then `strata-visual` compares every story and route state, light and dark, with the baselines), `npm run test:visual:update` (look at the diffs in `tests/visual/output/` first). Node 26 (`.nvmrc`).
- Python coverage is calculated from the unit suite only (`fail_under` in `pyproject.toml`). Web coverage is gated on unit + integration together (`web/coverage-floor.json`, read by `web/vitest.gate.config.ts`). Both floors only ratchet up.
- Style: dense, comment-the-why, long lines are fine (ruff line-length 400), pytest style tests (`def test_...` with `assert`; use `monkeypatch`/`tmp_path` instead of patching globals by hand).
- Cross-platform (Linux, macOS, Windows): OS differences (file locks, process liveness and termination, priority, how to start the CLI) live in `src/tubes/oslib.py`; do not import `fcntl` or call `os.kill(pid, 0)` elsewhere (on Windows that terminates the process).
- Reverse-proxy support: the server gives every page a relative `<base href>` back to its root (`with_base` in `server/app.py`), the web build uses relative asset paths (`base: './'` in `vite.config.ts`), and `BASE` comes from the page's base URL (`web/src/api.ts`); it is React Router's `basename`. Any URL the app builds for `fetch`, `<img>` or an external link must go through `withBase`; in-app links are router paths.
- CI is `.github/workflows/unit.yml` (lint, unit tests with coverage on Linux Python 3.11-3.13, macOS and Windows; web typecheck, coverage gate, build, Storybook build; visual regression) and `integration.yml` (integration tests on Linux, macOS and Windows, web component tests, weekly). `scripts/setup_env.ps1` / `setup_env.sh` build the environment from scratch.
- Docs live in `docs/`: `overview.md` (design brief), `implementation-plan.md` (milestones and next steps), `progress.md` (log of findings and decisions), `deploy.md` (running it on a server), `prompts/` (unattended agent prompts for backend unit, integration and web tests).
